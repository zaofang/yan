## 2. Design laws

These are normative. Every implementation decision not settled elsewhere in this spec MUST be resolved by them, in this order of priority.

1. **One semantics.** Yong defines all behavior. A surface MUST NOT add behavior that cannot be expressed in Yong; it may only add syntax. Niche surfaces (16.7) are exempt (R568): they may give their own items semantics of their own, under the boundary rules of 16.7. Xin, Wen and Chang are not exempt.
2. **Safe by default.** Outside `unsafe` blocks, a well-typed program MUST NOT exhibit undefined behavior, data races, use-after-free, null dereference, or an unhandled error or capability. Undefined behavior is the closed list in section 6.7; anything not on it is defined. `unsafe` is permitted only in the standard library and in modules marked `ffi`.
3. **Unambiguous text.** Every source text has exactly one parse and one meaning. The grammars are deterministic with one token of lookahead after the factorings given in sections 13, 15 and 16.6. Operator mixes that people commonly misread require parentheses.
4. **Five facts at the use site.** Mutation of a passed-in variable, possible failure, compile-time evaluation, concurrency, and capability use MUST be visible where they happen, by the marks defined in each surface. For a method call whose receiver is a mutable place, the receiver's `var` declaration is the mark (SQ29); in Xin, where local mutability is inferred, the mark is the receiver form together with the callee's `var` first parameter, which tools show as an inlay (R421). Everything else may be inferred.
5. **Nothing implicit at run time.** No implicit numeric conversion, no null, no exceptions, no hidden I/O, no hidden heap copies, no language runtime. Copies, moves and capability passing are explicit in Yong, even when the surfaces leave them implicit.
6. **Local reasoning.** Every item MUST be checkable from its own body plus the signatures and contracts of the items it references. No global inference across modules.
7. **Deterministic by default.** The result of a computation is a deterministic function of its arguments and of the values its capability operations return. Scheduling MUST NOT be observable except through `nondet`. Code that binds only deterministic handlers MUST produce bit-identical results on every run, scheduler, thread count and supported target, except where a stateful handler of a shared capability is used by tasks that may run at once (7.7, R342, R377).
8. **Canonical text.** Each surface has exactly one canonical printing of any program; for Chang, of any program together with its spelling notes, which are hash-neutral trivia (16.5, R518). The toolchain stores canonical text, and the formatter produces it. The Xin lenient reader MAY accept the deviations listed in section 14.4 and MUST normalize them.
9. **Depth is additive.** Annotations deeper in the layer stack (L1 to L6) are checked assertions. Adding one MUST never require rewriting code that does not use it.
10. **Familiar beats novel (Xin only).** With types, contracts and the constructs listed in section 14 removed, a Xin program SHOULD be valid Python 3.12. A deviation from Python needs evidence of benefit (law 11).
11. **Evidence-gated change.** After 1.0, a change to either surface MUST be justified by the measurements in section 23: model pass@1 and total tokens per solved task for Xin, and a randomized comparison for contested Wen syntax.
