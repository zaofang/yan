# Yan Core · Yan Agent · Yan — Language Specification 1.0 (draft)

Oct 31, 2026 · consolidated from v0.3 rev 338

This is the implementation specification for one programming system with two surface languages, **Yan Agent** (言信, written by language models) and **Yan** (言文, written and read by people), over one shared core, **Yan Core** (言核). The project, its toolchain and its binary `yan` are **Yan** (言). It is written for an engineering agent that will build the compiler, standard library and tools from this document alone.

**Status.** 1.0 draft, consolidated on 2026-10-31 from spec v0.3 (rev 338) and moved from the spec Claude Doc (rev 517) into this directory on 2026-11-01. Every accepted change row listed in `rows.toml` (Appendix A.1), and every resolved SPEC\_QUESTION SQ2 to SQ33, is folded into the body below, and wording that those rows superseded is gone. The v0.3 text, with its change tables, stays in `archive/v0.3.md`. Appendix A maps every row to the section that now carries it. Where this text and the archive differ, this text wins. The owner confirmed R1 to R14 as normative on 2026-10-31. The owner also chose, the same day, that stage-0-constant query plans compile automatically in release builds (section 11.9).

**How to read it.**

- Sections 3 to 12 define Yan, the semantics. Both surfaces are only syntax for Yan, so Yan is implemented first.
- Sections 13 to 16 define Yan Agent and Yan, their complete grammars, and how they map to Yan Core and to each other.
- Sections 17 to 21 define the standard library, the toolchain, packages and the registry, stability, and the agent features.
- Sections 22 to 25 define the implementation plan, the milestones, the conformance suite and the diagnostics catalogue. Build in milestone order (section 23); do not start a milestone until the previous one's acceptance criteria pass.

**Normative terms.** MUST, MUST NOT, SHOULD and MAY have their RFC 2119 meanings. Anything not marked normative is rationale or example. Where an example and a normative rule disagree, the rule wins; report the conflict as a spec bug.

**Spec bugs.** When something is ambiguous or contradictory, the implementer MUST NOT guess silently. Record the question in `SPEC_QUESTIONS.md` at the repository root, choose the option that best satisfies the design laws (section 2), and mark the code with a `SPEC-Q` comment naming the entry. The executable definition of the abstract machine is the reference interpreter's checked mode (section 6.1); where it and this prose disagree, that is a spec bug.

**Names.** The system was previously drafted as Fathom/Tern/Keel, then Ben/Fan, Ming/Jian and Yong/Jian. Since 2026-11-01 every name except Yong and Wen comes from Wang Xizhi's 兰亭集序 (R586). Treat any leftover Ben or Ming as Yong, Fan or Jian (简, `.jian`) as Xin, Fei (斐, `.fei`) as Chang and Shu as Lan. Since 2026-11-03 the project is Yan 言 (R774): treat Yong (永, `yong`, `.yong`) as Yan and Yan Core (`.yir`), Wen (文, `.wen`) as plain Yan (`.yn`), Xin (信, `.xin`) as Yan Agent (`.yag`), Chang (`.chang`) as Yan Notation (`.ynt`), and the niche names of 2026-11-01 as their "Yan <job>" names (16.7).
