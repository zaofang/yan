### 18.2 Diagnostics

Every diagnostic is one structured record. JSON form (normative field names; new fields only as optional additions with a `schema` version):

```
{
  "schema": 1,
  "code": "E501",
  "severity": "error",
  "item": "app.pricing.value",
  "file": "src/pricing.yag",
  "span": {"line": 14, "col": 9, "end_line": 14, "end_col": 14},
  "message": "index may be out of bounds",
  "notes": ["no bound on i is known here"],
  "fixes": [{"title": "use xs.get(i)",
             "edits": [{"span": {"line": 14, "col": 9, "end_line": 14, "end_col": 14},
                        "text": "xs.get(i)"}]}],
  "counterexample": null
}
```

Renderings from the same record:

- **Line** (default for Yan Agent and for agents, and `--format line`): one line per diagnostic, by the grammar of R294 below.
- **Prose** (default for Yan and for people at a terminal): by the rules of 15.5 and R296.
- **JSON** (`--format json`), **SARIF** 2.1.0 (`--format sarif`) and LSP diagnostics, all from the same record. `--format` takes a comma-separated list, so one run can emit several. Over MCP the model reads the line rendering and the harness reads the JSON (21.4, R295).

Rules:

- Report root causes only. A failing expression is marked and checking of its item continues around it (R291).
- A construct the toolchain does not implement yet is E017 at the construct's span, never a message without a record. The construct is marked as in R291 and checking continues around it (R649).
- Sort by file, line, column, then code; apply the cap after sorting. At most 10 errors per run by default (`--max-errors`).
- Codes keep their meaning forever. A code may be retired, never reused; tools key on codes, not wording.
- Every error with a mechanical fix MUST include it in `fixes`.
- The full catalogue is section 25.

**Lints.** Lints are W8xx diagnostics reported by `yan check`, each with a fix where one is mechanical. They warn by default and deny under `--strict` and `--level release`. A lint introduced in a minor release warns at every level, including --strict and release, until the next edition (R348). `@expect(code, reason="...")` on an item is the only suppression, and `@deny(code)` on an item makes that lint an error inside the item in every build mode (R797). `@deny` takes no reason, an `@expect` of the same code inside a `@deny` item is E277, and a `@deny` naming a code that is not a W8xx lint is E278. A dependency's `@deny` stays a warning in the consumer's build. and W810 reports one that suppresses nothing. `--strict` and `@expect` apply to the package's own code; diagnostics in dependencies are capped at warnings. Warnings outside W8xx follow their own rule (R379): W014 never denies, W111 follows the lint rule, and W420 is denied only where E603 applies. **Package lint sets (R819, R820).** `Package(lints=Lints(strict=True, deny=["W811", "style"], forbid=["rc", "panic"]))` is a literal manifest field that can only make the package stricter. `strict=True` makes every build of the package's own code behave as `--strict`; `deny` makes each named W8xx lint, or named std lint group, an error in every build mode as if every item carried `@deny`; `forbid` puts `@forbid(...)` on every function (5.7). Groups are defined by std and pinned per edition (R348). There is no package-level `allow`, `alloc` is not accepted in `forbid` (use the ceiling, 19.2), and an `@expect` of a code that a package, module or item `@deny` denies is E277. `@@deny(...)` and `@@forbid(...)` at the top of a file apply to the module, as `@@prove` does. The set is applied identically by `yan check`, `yan test`, `yan build` and the agent tools, never applies to dependents, and `yan test` fails on a denied lint before running tests. A workspace member does not inherit the root set; `Lints(workspace=True, ...)` opts in and may only add. The registry page and `yan add` show a published package's set. User-written analyzers are a non-goal for 1.0 (26.2).

The design behind R290 to R299 is the Yan diagnostics design.

**Record fields (R290).** The record gains optional fields under `schema` 1: `id` (short and unique within one response, written `#n` in line form), `item_hash` (the hash of the item the checker saw), `quote` (R293), `args` (the values of the template slots, R297), `labels` (secondary spans, each with text), `children` (nested notes and helps, each with an optional span) and `explain` (the code to pass to `yan explain`). A child of kind `habit` (R662) names a Python or TypeScript habit that triggered the diagnostic, as `{"kind": "habit", "lang": "python", "text": ...}`, and the Yan Core form for it. The toolchain's habit table covers at least the corpus of the learnability study; prose renders a habit child as `note:`, and the line form leaves it out. `notes` keeps the text of the children. SARIF output maps the item to a logical location.

**Recovery by marking (R291).** An expression that fails name resolution or typing is marked and given the error type, as in the marked lambda calculus (Zhao et al., POPL 2024), and checking of its item continues. A diagnostic whose span or inputs include a marked node is suppressed. Later phases skip marked subtrees, not whole items. Spans always point at surface text: an error in an operation inserted by elaboration (a copy, a move, a capability argument) is reported at the construct that caused it. Two diagnostics from one root cause are a toolchain bug, and the conformance suite tests for them.

**Fixes (R292).** A fix is an 18.3 patch with base hashes; editors derive span edits from it. `applicability` is `auto` (a meaning-preserving fix from the mechanical list of 21.4), `choice` (a fix that changes meaning, selected by a person or model) or `template` (a fix containing typed holes, filled through `hole_context`). Before an `auto` or `choice` fix is reported, the toolchain applies it in the query database and re-checks its item and dependents. The fix is reported only if it removes its diagnostic and adds none, and then carries `verified: true`. At most three fixes per diagnostic, best first. `cost` states a fix's run-time or precision cost in one phrase when it has one. `yan fix` and `autofix` apply only `auto` fixes.

**Quote anchors (R293).** `quote` is the text of the primary span, extended outward by whole tokens until it occurs exactly once in its item. It is always a valid `search` string for an 18.3 `edits` entry.

**Line format (R294).** The line rendering is normative and byte-identical across implementations: one line per diagnostic, with no colour and no excerpt. The fix kinds `fix`, `maybe` and `fill` mark `auto`, `choice` and `template` fixes. Newlines in fix text are written `\n`. Diagnostics with the same code and the same fix in one item collapse into the first line plus `(+k like this at l:c, ...)`. An empty `item` or `quote` is left out together with its separators, as for a syntax error outside any item or a patch rejection with no search text (R650).

```
line  = [ "#" n " " ] code " " path ":" line ":" col [ " " item ":" ] [ " " "`" quote "`" ] " " message
        { " | " note } { " | " kind ": " old " -> " new } [ " (+" k " like this at " locs ")" ]
kind  = "fix" | "maybe" | "fill"

#1 E501 src/pricing.yag:14:9 value: `xs[i]` index not proven in bounds | maybe: xs[i] -> xs.get(i)
```

**Agent repair channel (R295).** Over MCP, a result that carries diagnostics puts their line rendering in `content` and the JSON records in `structuredContent` (21.4). `apply_fixes` takes fix ids (`#2.1` is fix 1 of diagnostic 2) and applies them as one atomic patch. `check` and `check_patch` apply `auto` fixes before they answer and take an optional `max_tokens`; when the budget cuts, diagnostics with no fix come first, then the rest in the order above, and a last line says how many were held back.

**Prose rendering (R296).** A header with the code and a title, then the location, the excerpt with the primary span and labelled secondary spans, the rule as one line, each fix as a rendered diff with its cost, and `more: yan explain CODE`. A type mismatch marks the parts of the two types that differ. The voice is neutral: no "I" or "we", and no blame. Box drawing uses Unicode with an ASCII fallback; colour is off under `NO_COLOR` or when output is not a terminal; the explanation is linked with OSC 8; width follows the terminal, up to 100 columns.

**Message templates (R297).** Each code has one template set in Unicode MessageFormat 2.0: title, message, rule and fix titles, with a variant per surface, filled from `args`. Types and code inside a message are printed by the surface's printer (18.5), so a Yan message shows Yan syntax. The toolchain build fails if a Yan template uses a term from the list in 15.5. Messages are English in 1.0. A trait may carry `@diagnostic(on_missing="...", note="...")`, which supplies the message and a note for E221 on that trait; it never changes what compiles.

**Core error codes (R298).** E100, E102, E201, E202, E203 and E221 (section 25) cover syntax errors, type mismatches, argument counts, unknown fields and methods, and unimplemented traits. When a name in scope, a field, a method or a std module member is within edit distance 2 of the unknown name, E200 and E203 carry it as a `maybe` fix, nearest first, at most three (R651).

**Tested and scored catalogue (R299).** Every code has at least one `fail/` conformance test asserting its code, span and quote, and every fix kind it emits has a `patch/` test that applies the fix and checks clean. `yan explain` text and its broken and fixed examples are generated from those tests. Message wording is not normative. The evaluation harness (21.6) reports, per code, the share of diagnostics repaired on the first model attempt and the tokens per repair, and template rewrites are prioritized by those numbers (law 11).

### 18.3 Patch protocol

Models and tools change code only through patches. A patch is JSON:

```
{
  "module": "app.pricing",
  "base": {"value": "b3:9f2c...", "main": "b3:41aa..."},
  "replace": ["def value(...) -> ...:\n    ..."],
  "add": ["def vwap(...) -> ...:\n    ..."],
  "delete": ["old_value"],
  "edits": [{"item": "main", "search": "qty=10", "replace": "qty=20"}]
}
```

Semantics (normative):

1. A patch is atomic: all of it applies, or none.
2. `base` maps item names to the hashes the author saw. If any differs from the current hash, the patch is rejected with P001, and the response includes the current text of those items.
3. `replace` entries are complete items, matched to existing items by name (P004 if absent). `add` entries must not exist yet (P005) and are appended to the module. `delete` names must exist (P004).
4. `edits` apply exact string replacement inside the named item only. The search text must match exactly once within that item (P002 otherwise).
5. The result is printed canonically. With `--check`, the patch is rejected (P003) if it introduces any error in a touched item or its dependents, and the diagnostics are returned. When a patch changes an item's header, the response also lists every call site in the package that the change breaks, each with its diagnostic and fix, in the same round (R213).
6. A plain source file containing only whole items is also accepted as a patch: each item replaces the item of the same name, or is added if new. Patches to `.yn` modules carry Yan item text.
7. Every applied patch is appended to `.yan/oplog.jsonl`; `yan undo` and the MCP `undo` tool revert from it.

**Protected targets.** `check_patch` rejects a patch that touches any of the following unless it carries a human confirmation token (P006): test functions, `@test_support` items and items under `tests/` (the R300 test-hash closure); `pre`, `post`, `ex`, `invariant` and `decreases` clauses; a new item named by one of those clauses (R675); `package.yag` capabilities, `approvers` and `trust`; `yan.lock`; extern blocks and `ffi/` overlays; and agent configuration files. An implement-step patch never carries one (21.1). Weakening a package lint set (removing an entry or `strict=False`, R819) or a TLS profile (R825) also needs the token; additions do not.

### 18.4 Build, cache and test verdicts

- **Incremental builds.** The query database (salsa) caches per item and per instantiation; Cranelift compiles each instantiation to its own object fragment in parallel. Debug links use wild (Linux), ld-prime (macOS) and lld-link (Windows). A remote content-addressed cache is read by everyone and written only by CI. Hot reload swaps functions through a debug jump table (M2).
- **Test verdict cache.** A test that binds no real capability is a pure function of the hashes of every item it reaches, its handler bindings, its generator seed and the toolchain hash. `yan test` MAY reuse a stored verdict for an unchanged key and MUST mark it cached; `--no-cache` forces a run. Tests that bind a real capability with `with` are never cached. Until handler bindings and seeds vary, the key is BLAKE3 over the test hash, the identity hashes of every item of its module it reaches, and the toolchain hash, the BLAKE3 of the `yan` binary; a test that reaches a `with` is not cached. Verdicts live in `.yan/cache/verdicts.json`, and the MCP `run_tests` tool reads the same cache (R669).
- **Symbolic search (R609).** `yan test --symbolic[=bound] [item]` runs items on the checked interpreter with symbolic inputs and symbolic handlers for capabilities, and searches within the bound for inputs that violate a `post`, an `assert` or any panic kind. Each input found is written to `.yan/found/` as a proposed test. For a `pub` Yan Agent function with no `ex`, it proposes `ex` lines for approval. If R557 is adopted, `yan diff --semantic` uses it for bounded equivalence outside the decidable fragment.
- **Item facts (R612).** `yan why <item> <fact>`, where the fact is a capability, a `fail` member or a panic kind, prints the shortest chain of statements and callees that makes the item need it, one line and span per step. An empty chain means the declaration is unneeded, and its fix removes it.
- **Fuzzing and mutation.** `yan test --fuzz name` runs coverage-guided fuzzing over a property test's generators (LibAFL fork server); a crashing input is minimized and written to .yan/found/ as a proposed test (R300, R303). `yan test --mutate` scores how well tests catch injected bugs, pruning mutants by item hash.
- **Benchmarks** count instructions in CI and report copy, `Rc` and `Arc` events per site.

**Testing and debugging (R300 to R309).** Accepted 2026-10-31 from the testing and debugging design. R305 is in 7.6.

- **Approved tests (R300).** The package root holds `tests.lock`: the item path and *test hash* of every approved test function, `ex` clause set, snapshot file, regression input and stored trace, signed by `yan approve tests` with the 19.4 Sigstore flow. The `toolchain` capability cannot produce it. A test hash is the item's canonical Yan Core text with references to test-support items (items under `tests/` or marked `@test_support`) replaced by their full hashes and every other reference by path plus interface hash, so an implementation change keeps approvals and any change to a test, its helpers or fixtures breaks them. `yan test --gate`, which CI runs, MUST fail when a locked hash is changed (E014), missing (E015) or failing. Every other test is *proposed*: it runs and is reported but neither passes nor fails the gate. A shrunk property counterexample, fuzz crash, failing schedule or recorded panic is written to `.yan/found/` as a proposed regression test with its input; `yan approve tests` shows each one with its failing output. Path guards and P006 (21.1) remain as a second layer. The lock is enforced from M0; signing from M1.
- **Property tests (R301).** `Arbitrary` is derived for every type through `derived` (10.4); refinements in the 8.6 fragment generate inside their range without rejection. In a property test a parameter's default is its generator (`k: int = gen.ints(1, 8)`). `assume(c)` discards a case, and more than 10 times the case budget in discards fails the test. `target(score)` steers generation toward high scores; `note(v)` prints only on failure. The budget is 100 cases, `@cases(n)` per test, `--cases N` per run. The seed MUST derive from the test hash and the toolchain hash. `.yan/examples/<test hash>` keeps failing and best-target choice sequences and replays them first. `std.test.machine` provides stateful tests from a model, commands and postconditions, shrunk by the same passes.
- **Snapshots (R302).** `snap(v)` stores `v` printed as a canonical Yan Core literal (reflection, shortest round-trip floats, insertion-ordered dicts) in `snapshots/<module>/<test>.<n>.yir`, one file per call in call order; `snap_text(s)` stores raw text. New or changed output fails the test and writes `<file>.new`; `yan test --update` turns all of them into one patch, which stays proposed until approved (R300). Snapshot diffs report changed field paths.
- **Fuzzing and coverage (R303).** `--fuzz` mutates the choice-sequence bytes that property-test generators read, with edge coverage and comparison logging from the Cranelift debug build; `--fuzz name --ub` runs in the checked interpreter. `--for D` bounds time; `--fuzz all` round-robins with swarm-style weights. The corpus is `.yan/corpus/<test hash>/`, shared through the remote cache, which only CI writes. `yan test --coverage` reports region and branch coverage per item as LCOV and JSON; `--mutate` skips unreached mutants. Interpreter fuzzing in M1, native in M1b.
- **Schedule exploration (R304).** std adds the sched handler `pct(depth, runs)` (probabilistic concurrency testing). `yan test --explore` estimates first and runs `explore` when the count fits the budget (default 100,000), otherwise `pct(3, budget)`, and reports which ran; `@explore(handler)` pins one. `check_linearizable(machine, tasks, ops)` checks concurrent histories of an R301 machine against its sequential model; every std concurrent type has such a test. Failures write a shrunk schedule trace to `.yan/found/`.
- **Debugger (R306).** One trace query engine serves the DAP server, `yan debug` and an MCP `debug` tool. Native debug builds on Linux and macOS take fork checkpoints every N capability operations and reverse by restoring a checkpoint and replaying forward; finer reverse stepping uses the interpreter. Queries: `at(trace, loc, expr)`, `why(trace, loc, expr)` (dynamic dependencies of a value, including capability reads), `last_write(trace, loc, place)` and `diverge(trace, rev)`. MCP queries are stateless and token-budgeted. Debugger evaluation is pure and binds no capability; setting variables is allowed only in a live session. Interpreter in M1, native checkpoints in M2a.
- **Profiling (R307).** `yan profile --count` attributes instructions (hardware counters natively, abstract steps in the interpreter) to items and tasks, and `--diff REV` reports per-item deltas; `bench_` functions gate on the same counts, with wall time and confidence intervals reported beside them and baselines in `.yan/bench/`. Wall-clock profiles split off-CPU time by capability operation and call site. `yan profile --causal` virtually speeds up one line through the `pool` scheduler and reports the effect on `progress(name)` throughput, in M2b.
- **Tracing (R308).** Span ids MUST derive from the task-tree path and a per-task counter, and trace ids from the run seed, so equal inputs give identical traces; a production handler MAY draw the run id from `crypto_rand` at bind time. Span fields are evaluated only when the bound handler enables their level, and a static `log = null` binding removes span code. `@trace` opens a span named by the function path, recording `Show` arguments (`Secret` prints redacted). std provides OTLP, JSON-lines and Perfetto export handlers; `yan run --trace out.pftrace` writes one track per task.
- **Runner (R309).** Tests are `test_` functions, `ex` clauses and `bench_` functions anywhere in a package; files run in parallel and results are reported in a fixed order. A test that binds a real capability with `with` is an I/O test, found from its body with no attribute (R447). I/O tests are never cached, run last and get a wall-clock timeout, and all others get a deterministic step budget. There are no retries and no `@flaky`. A test containing a typed hole reports `incomplete`. `--format json` emits one record per test: id, test hash, approved or proposed, verdict, cached, instruction count, counterexample and repro command; the line format is one line per failure ending in `| repro: <command>`.

### 18.5 Formatter

The design behind this subsection is the Yan formatter design. `yan fmt` has no options.

- **One printer.** `yan fmt` is print of elaborate of lenient read, and `yan view --as S` is the same printer for surface S. A surface is a printer module: sugar selection (a left inverse of its elaboration), a token table with spacing classes, an indent unit and comment syntax. The document algebra and engine are shared.
- **Engine and cost.** The layout of each item is the optimum of the Π\_e printer under one cost: the sum over lines of squared columns past 100, then line count, compared lexicographically. Ties go to the left alternative of the choice operator. Output is defined by that optimum, so it does not depend on how the printer is implemented.
- **Group shapes.** A broken group puts one element per line with a trailing comma; a flat group has none. Broken binary chains break before the operator. A trailing closure, block or `par for` body stays on the call line. Method chains of three or more calls break one per line with a leading `.`. Bin-packing applies only to sequences of literals.
- **Indentation.** Yan Agent: 4-space bodies, and a broken bracket closes on its own line at the opener's indent. Yan: 2-space bodies and 4-space continuation for every broken header, of which the signature layout (15.3) is one case. Tabs are never emitted.
- **Trivia.** Comments; blank lines (at most one inside a body, none at its start or end, exactly one between items); literal spelling (radix and exponent form kept, digit grouping normalized to 3 decimal or 4 hex or binary digits where the author grouped). A trailing comment sits two spaces after the code. Author item order is module trivia; the formatter never sorts items.
- **Width** is display columns by UAX #11 over grapheme clusters. Trailing comments do not count toward width.
- **Docs.** Doc comments print as canonical Markdown, one sentence per line. Code fences are formatted by their surface from column zero, then re-indented. Ordinary comments are never reflowed.
- **Laws**, tested on every conformance program and on fuzzed core trees printed through every surface: idempotence; the round-trip laws of 16.5; the comment multiset and attachments survive; no line over 100 columns unless it holds an unbreakable atom; formatting one item never changes another item's bytes.
- **Stability.** Printing is frozen per edition and guarded by a golden corpus in the conformance suite. A layout change ships only in a new edition, except a fix for a violation of the laws.
- **Broken input.** An item that fails to parse is emitted byte for byte with its diagnostics; the rest is formatted. `yan fmt --check` exits non-zero on any change.
- **Yan Agent tuning.** Any Yan Agent layout choice the rules above leave open is settled by tokens per solved task on the evaluation harness and frozen before 1.0.
- **Tools.** `yan fmt --explain <line>` prints the cost terms that chose each break (M3). The language server may render elastic-tabstop alignment as virtual padding for table-shaped code; the bytes are never aligned (M3).
- **Speed.** The formatter caches per item, keyed by item hash, trivia hash, edition and surface. Targets: Ruff-class whole-repository speed and under 1 ms median per item.

### 18.6 Language server and editors

- The language server (lsp-server) uses UTF-8 positions. It shows inferred `uses` and `fail`, runtime-checked indexes, and copy and move sites as inlay hints, and evaluates watch expressions (`#>` in Yan Agent, `-->` in Yan). Tree-sitter grammars ship for Yan Agent (M1) and Yan (M3).

**Lenses (R265).** The language server offers two read-only views. The class view shows a type's fields, inherent methods and every trait impl in the package in one virtual buffer, and edits made there apply at their real locations. The fold view shows a loop whose body only assigns accumulators declared immediately before it as `fold (acc = init) for x in xs -> expr`. Lenses are never parsed, so they cannot affect the round-trip laws (16.5).

### 18.7 Debugging and profiling

Cranelift and LLVM output carry DWARF line tables and variable locations, with GDB and LLDB pretty-printers for `Option`, `Result`, `Str`, `Array` and `Table`. Native builds are debugged through lldb-dap. The interpreter's DAP server supports reverse execution from snapshots plus capability replay. Backtraces follow tasks and actors to their ancestors. Symbol mangling is specified and demanglable. Every build keeps frame pointers. The profiler samples per task (samply), writes flamegraphs and perf maps, reports copy, `Rc` and `Arc` events per site, and profiles allocation by swapping the `alloc` handler.

### 18.8 Distribution

`yan` ships through dist installers, a PyPI wheel and Homebrew. A package pins its toolchain with `yan = "1.x"` (20.3), and `yan toolchain` fetches and verifies newer toolchains when needed. Cross-compilation uses the bundled linker and Zig-style libc stubs, so no platform toolchain is needed.

### 18.9 Documentation (R310 to R319)

Accepted 2026-10-31 from the docs and learning design.

- **Doc model (R310).** A Yan Agent docstring and a Yan ` ---  ` comment elaborate to one `Doc` trivia node on the item; it is hash-neutral (3.6). Its language is CommonMark plus GFM tables, with three additions only: item links (`[Reader]`, `[std.io.Reader]`, `[text][path]`), resolved like a name at the item's scope; tagged sections opened by a line `Fails:`, `Uses:`, `Panics:`, `Safety:` or `See also:`; and fence tags naming a surface (`yag`, `yn`, `yir`, `ymt`) or `text`, where a trailing `!` (`yn!`) pins the surface. An untagged fence takes the file's surface. The first sentence is the summary. There are no doc attributes, hidden fence lines or per-fence flags.
- **Sub-item docs (RFC 0035, R846 to R848).** Tagged sections add `Args:`, `Attributes:` and `Variants:`. `Args:` holds one `name: text` entry per parameter, continuation lines indented, printed in parameter order; a parameter may instead be documented above it (`#:` in Yan Agent, `---` in Yan) in a signature broken one parameter per line, and the choice is kept by the `DocAbove` mark (16.5); a function may mix the two for different parameters but not both for one (E280). `Variants:` holds `Name: text` for a variant and `Name.field: text` for a field of an inline variant, printed in declaration order; a variant has no doc position of its own and the grammar does not change. `yan doc` shows each sub-item doc in the table of its parameters, fields or variants and the agent view carries them in the untrusted channel of 21.4; `yan doc --coverage` counts them beside item docs. W860 is always on; W861 is enabled in `yan.toml`.
- **Links (R311).** `yan doc` resolves each item link to the target's item hash, so renames and moves keep links valid; `yan fix` rewrites the source name after a rename. Links into dependencies pin to the version in `yan.lock`.
- **Outputs (R312).** `yan doc` builds one doc index from the `yan check` database and renders it three ways: a static HTML site with a client-side search index that works offline; a JSON index (`--json`) whose schema is versioned and frozen per edition (20.2); and an agent view (`--agent [path]`), Yan Agent only, holding signature, `uses`, `fail`, summary and `ex` lines, also written as `llms.txt` at the site root and served by the MCP `query` tool. The agent view uses the `pack_context` packing and the untrusted fenced channel (21.4); its layout is tuned by token measurement on the eval harness.
- **Surfaces (R313).** Signatures, `ex` lines and code fences are printed in the reader's surface by `yan view --as S` (16). The site defaults to Yan; a toggle switches every sample and is remembered per browser. Prose is never translated, and pinned or `text` fences are shown as written.
- **Item pages (R314).** In this order: signature; `uses` badges (a `pure` badge for none) and `fail` badges, linked to their types; summary and doc; `pre` and `post`; `ex` clauses as call and result, marked checked; tagged sections; facts (item hash, `@since`, deprecation and replacement, `@non_exhaustive`, layout of `@layout(c)` types, source link); relations (impls, implementors, fields, variants). A package page shows the union of its `pub` items' capabilities. `yan doc --coverage` reports `pub` items without docs.
- **Doc fences run (R315).** `yan test` compiles every code fence in doc comments and guide pages and runs it as a test under the test handler set of 7.3 (R377), with the in-memory file system seeded from `docs/fixtures/`. A fence fails on a compile error, a panic or a failed `assert`. Outputs shown under a fence (what it printed, and each `#>` / ` -->  ` watch value) MUST be generated by that run and are never authored. Fence verdicts and rendered outputs are cached by elaborated hash plus dependency hashes (R19). Fences are illustrations, not contracts: they are not part of item hashes and are not frozen; `ex` clauses and approved tests (R300) remain the contract.
- **Guide pages (R316).** `docs/*.md` files are Markdown with fences as in R310. `yan doc` renders them beside the API pages in the order `docs/index.md` lists, and `yan test` runs their fences as in R315. Fences on one page share a scope in order; a page MAY declare `uses` once in a front-matter fence, and its fences get only those capabilities.
- **Doc lints (R317).** W830 `pub` item without a doc comment; W831 item link resolves to nothing (fix: nearest name within edit distance 2); W832 a `Fails:` or `Uses:` section disagrees with the signature (fix: rewrite it from the signature); W833 fence tagged `text` parses as code in the file's surface (fix: retag).
- **Hosting and playground (R318).** On publish, the registry builds the version's docs hermetically from the published artifact with the pinned toolchain, records the doc build hash beside the package hash, and serves the static output beside the index; anyone can rebuild the same bytes. The playground is the checked interpreter built for wasm32-wasip2, running in the browser under the R315 handlers; every fence on the site and in the tour opens in it. Nothing runs on a server.
- **Learning set (R319).** The tour (about 70 pages; exercises are a signature, its `ex` clauses and a `...` body, graded by the `ex` clauses; served offline by `yan tour`), the book (1.x), the cookbook, the Python, Rust and TypeScript migration guides (R664), std API docs and this reference rendered by `yan doc` are packages whose `yan test` runs in CI. The book is not normative and cites spec sections for rules.
