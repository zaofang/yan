# 0034: Spelling marks from lowering to raise

- Status: draft
- Research: none; a read of `crates/yan-surface/src/lib.rs`, `crates/yan-elab/src/lower.rs`,
  `crates/yan-hir/src/raise.rs`, 16.5, and a local `tools/conform.py --laws` run on 2026-11-05
- Rows: filled in when accepted

## Summary

Law 1 of 16.5 (`yag(elaborate(F)) == F`) fails on choices the author made that elaboration erases:
an argument passed by keyword or by position, `x.len()` or `len(x)`, a `pre` that elaborates to a body
`assert`, a binding annotation, a hex literal, `@derive` and `@@prove`. The local baseline on
2026-11-05 is 83 pass, 51 fail, 75 skip. 16.5 already says Yan Core carries hash-neutral trivia in a
side table keyed by item hash and node path, and `yan-surface` has a `TriviaTable` type, but nothing
writes or reads it: Yan Core nodes have no path scheme, elaboration records nothing, and `raise` rebuilds
spelling by heuristics and stamps most HIR nodes with a dummy span. This RFC fills that gap: one node
path scheme defined in `yan-core`, a closed set of typed marks, elaboration as the only writer, `raise`
as the consumer, a strict mode that fails on marks `raise` did not use, and a companion check that
keeps law 1 from passing by copying text. It ends with a staged plan, one thread per step, keyword
arguments and annotations first.

## Decisions

### D1: node identity is item hash plus node path, from one walker

16.5 keys trivia by item hash and node path; this RFC defines the path. `yan-core` gains one function,
`yan_core::path::walk(item, f)`, that visits every markable node of an item in a fixed order and hands
`f` the node and its path. Elaboration and `raise` both use it, so writer and reader cannot disagree.

Markable nodes and their child indices:

| Node | Path |
|---|---|
| the item | `[]` |
| parameter k of a function | `[0, k]` |
| contract k | `[1, k]` |
| body statement | `[2, s]`, then for a nested block `b` of that statement, `[.., b, s']` |
| the call in a statement's right-hand side | statement path, then `0` |
| argument k of that call | call path, then `k` |
| a literal atom | its parent's path, then its slot |

Item-level marks on the module (`@@prove`) use the empty item key `""`.

Options weighed: source spans as ids (they exist in memory, but `raise` and `yan-opt` build Yan Core
with dummy spans, and a span is not stable across a reformat); a node id field on the Yan Core AST
(touches every construction site of a hashed tree, and printing must hide it); the path. Paths need no
AST change and are what 16.5 already says.

Elaboration does not know a node's final path when it emits it, because later passes (the move and
copy pass of R769) rewrite statements. It therefore records marks against the HIR span and the kind of
node, and a finishing step walks the elaborated item once and moves each mark to the first node in walk
order with that span and kind. Spans are only this join key inside one elaboration; they are never
stored.

Recommendation: the path, with spans as the transient join key.

### D2: marks are a closed, typed set

`yan-surface` gains `Trivia::Mark(Mark)`. `Mark` is a closed enum; each variant names one spelling
choice, and none carries source text:

| Mark | On | Records |
|---|---|---|
| `Keyword` | argument | the argument was passed by keyword |
| `Positional` | argument | the argument was passed by position where a keyword was allowed |
| `Method` | call | written `x.f(..)` |
| `Function` | call | written `f(x, ..)` |
| `Annotated` | `let` statement | the binding had a written type |
| `FromPre` / `FromPost` | `assert` statement | elaborated from a `pre` or `post` contract |
| `Derived(trait)` | item | an impl generated by `@derive(trait)` on the named item |
| `Prove` | module | the module had `@@prove` |

Literal spelling stays the existing `Trivia::Literal(String)` (18.5), the one variant with text, and it is
valid only if it denotes the same value as the node. `Trivia::Spelling(String)` stays for Yan Meta
(R518). `Trivia::Origin` stays for inserted nodes (R565).

Options weighed: free-text spelling per node (a mark could hold the whole written argument list, which
makes law 1 a copy and tests nothing); deviations from `raise`'s defaults only (smaller, but it ties
the writer to `raise`'s heuristics, so every heuristic change moves marks); facts as written. Facts
cost a few entries per call and keep elaboration independent of `raise`.

Recommendation: a closed enum of facts; adding a variant is a row.

### D3: an item with marks is authoritative

Elaboration writes the name table (R519) for every item it lowers, so an item with a name-table entry
came from source. For such an item `raise` reads marks as facts: an argument without `Keyword` is
positional, a `let` without `Annotated` prints no type. For an item without an entry (hand-written
`.yir`, `yan-opt` output, a patch) `raise` uses its current heuristics, which stay as 16.5 requires for
unmarked Yan Core.

Recommendation: presence of the name-table entry decides.

### D4: elaboration is the only writer; the HIR already holds the choices

Every listed class is still visible in the HIR that `yan-elab` lowers: `Arg.name`, an `Attr` call
against a `Name` call, `Contract::Pre` and `Contract::Post`, a binding's written type, the integer
literal's text (before `int_text` normalizes it), and item decorators. So the surface lowerings
(`yan-yag`, `yan-yn`) do not change, and the marks work for Yan Agent and Yan at once. `elaborate_in`
returns `(y::Module, TriviaTable, Vec<Diagnostic>)`, and `Loaded::Ready` carries the table.

A class the HIR erases would need a surface-lowering note into the HIR first; none of the classes
below does.

Recommendation: write marks in `yan-elab` only.

### D5: raise consumes marks and validates each one

`raise(m, std)` becomes `raise(m, trivia, std)`. Each mark is checked against its node before use:
`Keyword` needs a parameter of that name that is not positional-only, `Method` needs a receiver,
`FromPre` needs an `assert` before the first other statement, a literal spelling must parse to the
node's value, `Derived(t)` needs an impl of `t` for the item. A mark that fails is dropped and the
default prints, as 16.5 says for a stale note. `raise` returns the set of marks it consumed.

`raise` also stops stamping new HIR nodes with the dummy `AT` span where a Yan Core span exists, so a
strict-mode report points at source.

### D6: strict mode fails on marks raise did not use

A mark that `raise` neither consumed nor dropped by D5 is a writer and reader out of step: either
elaboration marked a node `raise` never visits, or the walker moved. In normal use `yan view` ignores
it. Under `yan view --strict` and `tools/conform.py --laws` it is an error naming the mark, item and
path, and a dropped invalid mark is reported too, since elaboration should never write one.

The code is a new one in the E2 family, assigned in the writing PR. E201 is the type-mismatch code;
reusing it would make the R567 inner-code tables ambiguous.

Recommendation: strict mode as above, new code.

### D7: law 1 keeps testing raise

Marks only choose between spellings `raise` can already build from Yan Core; they never supply a
node. Two checks keep law 1 meaningful:

1. Law 1 as written, byte for byte, with the table and in strict mode (no unconsumed or invalid marks).
2. A bare companion, run on every case law 1 runs on: raise with an empty table, print, elaborate the
   result, and compare item hashes with `elaborate(F)`. This is law 3's shape for Yan Agent and keeps
   the heuristics of D3 correct.

A case that passes 1 and fails 2 shows a mark covering for a raise bug, and is reported as a failure of
law 1.

### D8: in memory only for now

Marks live from `elaborate` to `raise` inside one load. Storing a table beside `.yir` text, and keeping
marks across an edit (16.5's "dropped after an edit"), wait until a stored Yan Core form needs them.

## Staged plan

One thread per step, in order. Each step runs `tools/conform.py --laws` locally and reports the law 1
counts against the baseline above (83 pass, 51 fail, 75 skip); a step may not lower the pass count or
make the bare check of D7 fail on a case that passed it before. No step edits `tests/` or
`conformance/`.

1. **Plumbing.** `yan_core::path::walk`; `Mark` in `yan-surface`; `yan-elab` and `yan-hir` depend on
   `yan-surface`; `elaborate_in` returns a table (names table only); `Loaded::Ready` and `yan-ide::view`
   pass it to `raise`; `raise` returns consumed marks; `--strict` on `yan view`; `conform.py --laws`
   adds the bare check and strict mode. Accept: law 1 counts unchanged; crate selftests cover the walker
   on one item of each statement kind and the span join with two nodes sharing a span.
2. **Keyword arguments.** Elaboration writes `Keyword` and `Positional` on every value argument of
   every call it lowers from a HIR call; `std_args` and the user-function call path read them under
   D3. Accept: no law 1 failure whose first difference is a named against a positional argument; the
   bare check passes wherever it passed before.
3. **Annotations.** `Annotated` on `let`; `drop_inferred` and `annotation` read it under D3. Accept: no
   law 1 failure on an added or dropped binding type.
4. **Method or function call.** `Method` and `Function` on calls `raise` turns into builtins or
   methods (`len`, the `TYPE_MODULES` path). Accept: no failure on `.len()` against `len()` or the same
   pair for another builtin.
5. **Contracts.** `FromPre` and `FromPost` on the `assert` statements elaboration emits for non-pure
   `pre` and for `post`; `raise` moves them back into the contract list and drops the `out` binding
   elaboration added. Accept: no failure on `pre` or `post` against `assert`.
6. **Literal spelling.** Elaboration writes `Trivia::Literal` for an integer literal whose text is not
   its decimal form; `raise` prints it after checking the value. Accept: no failure on a hex, octal,
   binary or underscored literal.
7. **Decorators.** `Derived(t)` on impls `@derive` generates and `Prove` on the module; `raise` drops
   the generated impls and prints the decorator; item attributes with arguments stop being an
   `Unraised` case. Accept: no failure on a dropped `@derive` or `@@prove`, and the skip count falls by
   the cases that were skipped for attributes with arguments.

Steps 2 to 7 are independent once step 1 lands; the order is by failure count in the baseline.
