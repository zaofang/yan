Takeaways. The hard foundations (incremental database, lossless tree, canonical printer, structured
diagnostics with verified fixes) exist. What is missing is a protocol shell, a position model with byte
offsets, an analysis layer for symbols and references, error recovery inside items, and every editor-side
artifact except one `.yn` TextMate grammar.

## 2. Target feature list, prioritized

P0 is the floor for "usable"; P1 is "first-class"; P2 is where Yan is better than peers; P3 can wait.

### P0: usable

1. **Highlighting** for `.yag` and `.yn`: TextMate (VS Code, Sublime, GitHub fallback, JetBrains via bundle) and
   tree-sitter (Neovim, Helix, Zed, GitHub). One definition of keywords and token classes, generated.
2. **Diagnostics** on change, with related locations (`labels`), notes, code, and `yan explain` link.
3. **Formatting** (document and range) from `yan fmt`'s print of parse; format on save. Zero options (spec).
4. **Hover**: type of any expression or binding, signature, doc comment with `ex` lines, `uses` set, `fail` type.
5. **Go to definition** within a module, then across modules and packages (needs RFC 0084 slice 2a/2b).
6. **Document and workspace symbols**, outline.
7. **Code actions from fix-its**: every verified `auto` fix becomes a quick fix; "fix all" maps to `yan fix`.

### P1: first-class

8. **Completion**: names in scope, fields, methods, std items, `uses` capability names, imports, keywords.
   Needs recovery inside items (section 5).
9. **Find references** and **rename**, item-hash keyed so a rename survives a move (spec 18.9 already says links
   resolve to item hashes). Rename across a package, preview before apply.
10. **Signature help**, **document highlights**, **folding**, **selection range** (from the CST).
11. **Semantic tokens**: distinguishes capability, handler, `move`, `sink`, `inout`, comptime values, `unsafe`.
12. **Inlay hints**: inferred types (exists), inferred `uses` and `fail` (exists), plus parameter names, the loop
    and fold lenses, inferred cost bounds on functions with no clause (spec 8).
13. **Test explorer**: `test_` functions and `ex` lines as tests, run and re-run from the gutter, verdict cache
    (spec 18.4) shown as "not rerun, unchanged".
14. **Doc preview**: render `yan doc` output for the item at the cursor (needs `yan doc`; see roadmap).
15. **Call hierarchy** and **type hierarchy** (trait impls).

### P2: Yan-specific wins

16. **Ownership view**: show moves, last uses, drop points, copy and `Rc`/`Arc` sites as inlay hints, with a
    toggle. Spec 4 says ownership facts are computed once by `yan-check` and recomputed on demand; the server
    asks that analysis and does not keep a second representation (CLAUDE.md practice 12).
17. **Capability ceiling**: per function the inferred `uses` as a hint; per package the ceiling and who grants
    what; a "who can reach `net`" lens fed by `yan audit`; diagnostics when a closure captures a capability
    its callee does not declare. Show `unsafe` and `uses none` claims (what `yan audit` lists) as code lenses.
18. **Determinism and identity**: show the item hash (salted and identity) on hover, flag in the editor when an
    edit changes an item's identity versus formatting only (the no-op certification in `yan review`, RFC 0067).
19. **Surface switch**: "Show as Yan Agent / Yan / Yan Core" as a virtual read-only document through the
    canonical printer; later, a two-way edit where the edit applies to the real file via `yan patch` (the spec's
    lenses already define this for the class view).
20. **Agent-surface editing**: typed-hole context (`hole_context` exists), a "fill this hole" action that builds
    the `pack_context` bundle for an agent, patch-protocol (`yan patch`) application of agent proposals with
    undo through `.yan/oplog.jsonl`; a diff view per item hash from `yan review`.
21. **Watch expressions**: `#>` (Yan Agent) and `-->` (Yan) lines evaluated on the interpreter as pure code,
    shown inline. Spec 18.6 already requires it; it is a sandboxed run, so it needs cancellation (section 3).
22. **Trace-aware features** after record/replay lands: inline values from a recorded run, "why is this value
    this" using the trace query engine, trace diff.

### P3: later or cut

Call-graph visualization pane, notebook UI, refactoring beyond rename (extract function, change signature),
semantic search UI, spell-check of docs, per-surface features for niche surfaces (each of the 16 other
surfaces gets highlighting only until it is real).

## 3. Architecture

### 3.1 One binary: `yan lsp`

Recommendation: **`yan lsp` is a subcommand of the one `yan` binary**, built on `yan-db` and `yan-ide`, with a
thin `yan-lsp` crate that is only the protocol shell (`lsp-server`, as spec 18.6 and 22 already say). Reasons:

- The server is a projection of the same query database the CLI uses; a separate binary means a second build,
  a second version, and the version skew that hurts zls and the Python-wrapper LSPs (all [I]).
- gopls, rust-analyzer's `rust-analyzer` binary, `gleam lsp` and `ruff server` ship with or beside the tool [I].
  One download, one version, one `yan --version` to report in bug reports.
- Self-hosting (#851, S5) ports `yan-ide` and `yan-lsp` to Yan. Keeping the shell thin and the analysis API
  protocol-agnostic is what lets the port be checked against a golden (#870 already asks for
  "LSP capabilities fixed as a lead-approved golden"). Rule: no LSP types below `yan-lsp`.
- `yan mcp` and `yan lsp` should share one analysis session type, so an agent and an editor see the same
  answers. The spec 22.2 diagram already shows `yan-ide` shared by all three.

Rejected: a separate `yan-ls` distribution (version skew, double packaging); a Python server such as pygls
(project memory recorded the early idea; the spec and the self-host plan now point at Rust then Yan).

### 3.2 Incrementality and cancellation

Today `front`, `load` and `diagnostics` are per file; one keystroke reparses and rechecks the whole module,
which is fine for small modules and wrong for large ones. Plan:

- Keep salsa. Add cancellation: a new input write cancels in-flight queries via salsa's unwind, and handlers
  return `ContentModified` (the rust-analyzer approach [I]). Today nothing in `yan-db` handles it [V].
- Split `load`-level queries per item where the elaborator allows, keyed by item hash. The hash-keyed items
  already exist [V]; what is unmeasured is how much of `check` can be reused per item. This is the same item
  as the "hash-keyed incremental compilation" gap in the 2026-11-13 forum study; the language server is its
  first consumer, so measure here, not in a separate effort.
- Two tiers of answer: **syntax-only** (parse, highlights, folding, outline, format) returns in milliseconds and
  never waits on the checker; **semantic** (types, diagnostics, references) follows. Publish diagnostics in two
  passes: parse errors immediately, checker errors after a debounce.
- Budget (proposal): syntax answer under 20 ms, a one-line edit to diagnostics under 200 ms on a 20-file
  package (the #381 acceptance sample), measured with callgrind per CLAUDE.md practice 6, not wall time.

### 3.3 Positions

LSP defaults to UTF-16. LSP 3.17 lets the server negotiate `positionEncoding`; spec 18.6 says UTF-8. Add byte
offsets to `Span` (or a `yan-ide` position type derived from the CST) and negotiate `utf-8`, falling back to
UTF-16 conversion for clients that do not offer it (Sublime, older VS Code). The yn column inconsistency in
section 1 must be fixed first.

### 3.4 Error recovery

The single largest dependency. Completion, hover and go to definition all work on code that is mid-edit.
Item-boundary recovery means a syntax error inside a function body blanks that function for every query.
Needed: statement-level and expression-level recovery in both parsers (hole nodes in the CST, as rust-analyzer
and Gleam do [I]), and a checker that tolerates a hole without cascading diagnostics. The typed-hole concept in
Yan Agent (`hole_context`) is a natural fit: an unparsed expression becomes an implicit hole of unknown type.

### 3.5 Debugger (DAP)

Spec 18.7 says one trace query engine serves DAP, `yan debug` and MCP. Plan, in this order:

1. Interpreter DAP: breakpoints, step, variables, call stack across tasks and actors, watch expressions bound
   to no capability (spec: evaluation is pure). Reverse execution from snapshots plus capability replay.
2. `--ub` runs: the `run --ub` design (research 2026-11-14) adds undefined-behaviour checking; surface its
   report as exceptions with a data breakpoint style stop.
3. Native: lldb-dap against DWARF from Cranelift and LLVM, with pretty-printers for `Option`, `Result`, `Str`,
   `Array`, `Table`. The editor extension only configures the adapter; Yan ships the printers.

`yan debug` does not exist yet [V]. DAP is a P2 stage, not a first-release item.

### 3.6 Tree-sitter grammar

Tree-sitter is a separate artifact from the LSP and serves GitHub, Neovim, Helix, Zed, Emacs (`treesit`),
difftastic and structural tools. It is the only way to reach highlighting in editors that have no LSP-side
semantic tokens, and it is what GitHub linguist uses to highlight on github.com.

- `yan-ebnf` already holds each surface's grammar as data and emits three formats [V]. A fourth emitter,
  `grammar.js` for tree-sitter, would keep one source of truth for lexical structure [I]. Caveat: tree-sitter
  grammars for layout-sensitive syntax (indentation) need a hand-written external scanner in C; the emitter
  cannot generate that. Yan Agent and Yan both use indentation [V] (`MAX_DEPTH` indentation unrolling in the
  grammar emitter), so expect one scanner per surface family.
- Acceptance (from #383): the grammar parses every `.yn` conformance file; add the same for `.yag`, plus a
  highlight query corpus, a `locals.scm`, `folds.scm`, `indents.scm`, `injections.scm` (doc comments, f-string
  expressions).
- Conformance check: a CI job that runs the tree-sitter parser over `conformance/` and `examples/` and compares
  the error-node count to zero. Same job as the TextMate sample tests.

### 3.7 Distribution

- `editors/vscode/` extension: thin client (`vscode-languageclient`), downloads or finds `yan`, registers
  language ids, TextMate grammar, themes, snippets, debug adapter config, a "Yan: restart server" command.
- Publish to the VS Code Marketplace and **Open VSX** (needed for VSCodium, Cursor, Windsurf, Gitpod, Theia).
- `tree-sitter-yan/` as its own directory (`tree-sitter-yag` and `tree-sitter-yn` likely split) with a
  `tree-sitter.json` and highlight queries; published to crates.io and npm, and referenced by nvim-treesitter,
  Helix `languages.toml`, Zed extension.
- Editors other than VS Code get a config snippet and a documented `yan lsp` invocation, not a bespoke plugin,
  until demand exists.

## 5. Lessons from other servers

All [I]: from background knowledge, not checked against current sources in this study. Treat as hypotheses for
the design review.

| Tool | Copy | Avoid |
| --- | --- | --- |
| rust-analyzer | Salsa with cancellation by unwinding; lossless syntax tree as the base of everything; hole nodes for recovery; syntax-only fast paths; custom LSP extensions kept to a minimum and documented; "the server is a library with a thin shell". | Letting the macro and build-script story become a second analysis engine; heavy startup indexing with no progress; unstable custom extension surface. |
| gopls | Lives in the toolchain repo and ships with it; one process per workspace; stability and a documented feature matrix; careful `go.work` workspace handling; command-line `gopls` subcommands that call the same code (check, rename) for testing without an editor. | Memory growth on huge workspaces; settings sprawl. |
| Pyright / Pylance | Speed from a hand-tuned checker; clear modes (basic, strict); hover that shows the inferred type simply. | Pylance's closed-source split (ownership of the experience in a proprietary layer); long-lived inference cascades with no incremental frame. |
| ruff server / ty | Moved from a Python wrapper (`ruff-lsp`) to a native `ruff server` in the main binary: same as `yan lsp` in one binary. ty: salsa-based, treat editor use as the primary design target from the start. | Two code paths for CLI and editor that drift apart; shipping the server before the checker's recovery is solid. |
| Gleam | Language server inside the compiler binary; excellent code actions generated from compiler knowledge; fast because the compiler is incremental and error-tolerant. | (Few; pace of features is tied to compiler pace.) |
| Roc | An LSP that tracks the compiler's rewrite; shows what happens when the server is built against an unstable checker. | Starting the server before the front end API settles. |
| zls (Zig) | Community server tracking the compiler; works without running the compiler. | Maintaining a separate semantic model: zls lags comptime and the compiler. This is the argument for the single-binary choice. |

Yan-specific reading: Yan's selling point is one analysis (ownership, capability, cost) shared by tools. The
server must reuse `yan-check` and never grow a lightweight second analysis for speed (practice 12, "one fact,
one representation").

What to cut or defer for 1.0 (spec 23 / RFC 0064 keeps language server and Yan tree-sitter in M3, VS Code
extension in polish): notebook and live-value UI (already 1.x), call and type hierarchy, JetBrains native plugin,
Sublime, the 16 niche surfaces beyond highlighting, extract-function refactorings, `.yd` beyond highlighting and
manifest diagnostics. The first public editor release should be E1 + E2 + E3 + most of E4 in VS Code
and Neovim/Helix via tree-sitter (E6).

Dependencies the plan cannot avoid:

1. **Incremental front-end performance**: unmeasured today for module-sized edits; E5 gates the "fast" claim.
2. **Error recovery in the parsers**: gates completion, resilient hover, and rename in broken files (E4).
3. **Stable diagnostic spans**: byte offsets, consistent column units, secondary labels. E0.
4. **Cross-module names** (RFC 0084 slice 2a and later): gates E3.
5. **Position of the self-host port** (#851, #857): the golden transcripts and the protocol-agnostic `yan-ide`
   API are what make the Rust-to-Yan port checkable. Do not let the Rust server grow behaviour the golden does
   not cover.
6. **`yan doc` and `yan debug` do not exist**: E8 and E9 wait for them.

## 7. Risks

- Building the server on an unrecovered parser and then bolting recovery on later changes every query's inputs.
  Mitigation: E4 before any completion promise.
- A second semantic model for speed (the zls trap). Mitigation: review rule in the PR template for `yan-lsp`
  and `yan-ide`: new analysis goes into `yan-check` first.
- Extension surface sprawl: eighteen surfaces, eighteen extensions. Mitigation: only `.yag`, `.yn` (and `.yd`)
  get language support before 1.0; others get TextMate stubs generated from `yan-ebnf` token classes.
- Brand: the extension icon and linguist entry use brand marks that `TRADEMARK.md` restricts. Mitigation: lead
  approves marketplace listings and icon use.
- Marketplace publishing needs a publisher account and a signing identity owned by the lead.

## 8. Decisions for the lead

Labels D1 onward. Recommendation first.

- **D1. Server shape.** Recommend: one `yan lsp` subcommand in the toolchain binary, protocol shell in
  `yan-lsp`, analysis in `yan-ide`, no LSP types below the shell. Alternative: a separate `yan-ls` binary.
- **D2. Order.** Recommend: highlighting and VS Code shell first (E1), then server skeleton (E2) and
  navigation (E3), then recovery and completion (E4), tree-sitter in parallel (E6). Alternative: tree-sitter
  first, so GitHub and Neovim users get value before the server.
- **D3. Positions.** Recommend: byte offsets in `Span`, negotiate `utf-8`, UTF-16 fallback only for clients that
  need it. Alternative: UTF-16 everywhere.
- **D4. Recovery before completion.** Recommend: statement- and expression-level recovery with hole nodes is a
  prerequisite stage (E4) and a named gap issue. Alternative: ship completion on item-boundary recovery and
  accept that it works only between items.
- **D5. Tree-sitter source of truth.** Recommend: generate the token and rule portions from `yan-ebnf`, hand-write
  only the external scanner; CI compares against the conformance corpus. Alternative: hand-written
  `grammar.js` per surface.
- **D6. Editor tier.** Recommend: first release VS Code (and Open VSX), Neovim, Helix; Zed and JetBrains
  after; Emacs, Sublime by config only. Alternative: VS Code only.
- **D7. `.yd`.** Decided (lead, 2026-11-17): the spelling is `.yd`. Registered in the TextMate grammars and the
  VS Code extension (`yd.tmLanguage.json`, language `yan-data`). Still to do: `.gitattributes` entry, manifest
  diagnostics with E1/E2, and the file icon pair in `brand/`. Collision check on 2026-11-17: no `.yd` in
  github-linguist `languages.yml` (main) and no VS Code Marketplace extension contributing `.yd` found by
  extension-text query; neither source is exhaustive.
- **D8. Debugger.** Recommend: DAP after the trace query engine, interpreter first, native via lldb-dap.
  Alternative: native-only first.
- **D9. Agent-surface editing.** Recommend: post-1.0 stage E11 that shares one analysis session with `yan mcp`.
  Alternative: pull forward as the first differentiator.
- **D10. Distribution and trademark.** Recommend: the lead owns the marketplace publisher account, extension
  name and icon use; ask the lawyer before submitting the linguist entry. Alternative: publish under the
  Zaofang account.
