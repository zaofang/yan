# Yan Delegate 言代 (`.ydl`): syntax and semantics study

Status: brainstorm study, 2026-11-04. Not normative. No spec rows, no diagnostic codes. Every code
block below is a proposal; where it disagrees with `spec/`, the spec wins. Names are frozen (Yan
Delegate, 言代, `.ydl`); only the syntax inside the file is open.

Where it stands today: R545 (spec 16.7) lists the surface as research, "contracts whose bodies are
generated by the agent loop and pinned by hash", lowering to "functions with pinned bodies; Yan Agent
holes (R212) before a body exists". RFC 0002 D10 has one example with a `dream` keyword, and
`docs/surfaces.md` section 14 has a MOCK grammar. This study tests that sketch, offers five
alternatives that each push one axis, and mixes them into one recommended design.

## 1. Methodology and process

**Brief.** Antonio asked for one study per surface: research the market and the literature, brainstorm
five proposals that each optimize one axis, mix and match, and document the process. The target taste
is elegant, concise, powerful, expressive, opinionated without being obnoxious.

**What I read in the repo (narrowly).**

- `docs/surfaces.md` section 14 (the MOCK grammar and example) and the status table.
- RFC 0002 D10 (the one example, idea, lowering, open questions, first slice).
- Spec 16.7 rows R545 and R568, the N1 to N9 admission rules, and the two-routes rule.
- Spec 21.1 (spec gate, spec freeze, P006, W806, R675 frozen meaning, R617 reference loop), 21.2
  (typed holes, `hole_context`), 21.5 (provenance, `yan review`), 21.6 (eval harness).
- Spec 8.4 (contract language: `pre`, `post`, `ex`, `invariant`, `decreases`, `cost`; `out`; bounded
  quantifiers), 14 R211 (proven, refuted, unknown), law 4 (the five facts).
- Spec 13 keyword table (to keep new words soft and avoid collisions), R529 (synthesis from examples).
- `examples/tally/g5_tally.yn` for the house style of plain Yan headers and contracts.

**What I searched.** Spec-driven development tools (Tessl, Kiro, GitHub Spec Kit), vericoding and
verified synthesis (Dafny, Verus, Lean; Clover; AutoVerus), LLM-written specifications (nl2postcond),
interactive intent clarification (TiCoder), declarative LLM programming (DSPy signatures, Marvin-style
AI functions), classical synthesis (Sketch, Myth, Synquid), content-addressed code (Unison), LLM
non-determinism in code generation, test hacking and specification gaming, agentic property-based
testing, and developer trust surveys. Sources are in section 2 with a confidence mark each.

**What I tried.**

1. Five tasks, written in every proposal: `slugify` (pure text, examples plus properties),
   `dedupe_emails` (the RFC's own example), `popcount` (an optimization: a fast body against a slow
   reference), `fetch_json` (failure and capabilities: network, clock, retry), and `impl Ord for
   Version` (a delegated trait implementation). The tasks were chosen to cover the five facts of law 4
   and the three kinds of spec (examples, properties, reference).
2. A hand ambiguity experiment: for each spec, write two plausible bodies that both pass it and find an
   input where they disagree. Results in section 3.3; they drive the central idea of the mix.
3. A strawman experiment: check whether constant or trivial bodies (`[]`, the input unchanged, the
   first example's answer) satisfy the `post` lines. The RFC's own `dedupe_emails` spec fails this
   test (section 3.3).
4. A size count of the `slugify` sample in each proposal (non-blank characters and lines), as a cheap
   proxy for agent token cost and reading load (section 5).

**How the mix was made.** Each proposal was scored on the seven axes in section 5. For each design
question (keyword, example form, property form, where provenance lives, how review works, how bodies
regenerate) the mix takes the best-scoring answer unless it breaks a Yan law, then checks the result
against N1 to N9.

## 2. Findings from research

Confidence: **high** means a primary source read for this study; **medium** means a primary source's
abstract or a reputable secondary summary; **low** means my inference.

### 2.1 The market: spec-driven development

- **Three levels.** Böckeler (martinfowler.com, 2025) sorts tools into spec-first (spec written before
  the task, then discarded), spec-anchored (spec kept and evolved with the feature) and spec-as-source
  (humans edit only the spec). Kiro is mostly spec-first, Spec Kit spec-first with spec-anchored
  ambitions, and Tessl the only one exploring spec-as-source. Yan Delegate is spec-as-source with a
  twist: the generated body is pinned and checked in, so the build is not generative. (high)
- **What goes wrong.** Same article: specs balloon (a small bug became 4 user stories with 16
  acceptance criteria in Kiro), Markdown spec files are harder to review than code ("I'd rather review
  code than all these markdown files"), agents ignore instructions and duplicate classes, and Tessl
  produced different code from the same spec across runs, improved only by making the spec more
  specific. The author fears "the downsides of both MDD and LLMs": inflexibility and non-determinism.
  (high)
- **Tessl's mechanics.** Generated files carry `// GENERATED FROM SPEC - DO NOT EDIT`, tags such as
  `@generate` and `@test`, an API section the maintainer controls, and a 1:1 spec-to-file mapping.
  (high, via the same article)
- **Lesson for Yan.** Every market spec is prose (Markdown, EARS requirements). None is checkable. Yan
  already has a contract language with a solver and a three-outcome checker (R211); the opening is a
  spec that is short, typed and machine-checked, so its size stays near the code's and its review is
  cheaper than the body's. (low, inference)

### 2.2 Verified and spec-directed synthesis

- **Vericoding works for Dafny, less elsewhere.** A 12,504-spec benchmark (Dafny, Verus, Lean; POPL
  2026 Dafny workshop) reports off-the-shelf LLM success of 82% in Dafny, 44% in Verus and 27% in
  Lean; natural-language descriptions did not significantly help, and pure Dafny verification rose
  from 68% to 96% in a year. Formal specs plus a verifier are a viable target for model-written
  bodies, and the prose is not what makes it work. (medium, abstract)
- **Clover** checks three-way consistency between code, docstring and formal annotations; it accepted
  up to 87% of correct Dafny programs and no adversarial incorrect ones, and found 6 wrong programs in
  a human-written dataset. Consistency between independent artefacts is a strong filter. (medium)
- **AutoVerus** (OOPSLA 2025) generates Verus proofs with LLM agents in phases modelled on human
  experts. Proof and body can be generated together if the checker is the arbiter. (medium)
- **LLM-Modulo** (Kambhampati et al., ICML 2024): LLMs propose, external sound verifiers decide. This
  is Yan Delegate's architecture: the model is a generator, `yan check` and the solver are the
  critics, and only checked output is pinned. (medium)
- **Classical synthesis.** Sketch (Solar-Lezama) fills holes in a programmer-written skeleton; Myth
  (Osera and Zdancewic) synthesizes from types and examples; Synquid from refinement types. Each shows
  that partial structure plus a spec narrows the search a great deal. Yan already cites Myth and Hazel
  for R529. (medium)

### 2.3 Specs written or read by models

- **nl2postcond** (Microsoft Research): LLM-generated postconditions were generally correct and caught
  64 real historical bugs in Defects4J. The paper measures both correctness and discriminative power,
  the ability to reject wrong code. A spec that is true but weak is useless. (medium)
- **TiCoder** (Lahiri et al.): the tool generates tests, asks the user whether each is the intended
  behaviour, and prunes candidate programs. Average absolute pass@1 gain of 45.97% within 5 user
  interactions (idealized feedback), and lower cognitive load in a 15-person study. Asking the human
  about disagreeing inputs is cheap and very effective. (medium)
- **Agentic property-based testing** (NeurIPS 2025): an agent wrote Hypothesis properties for 100
  Python packages; 56% of its bug reports were valid, 86% of the top-ranked 21. Models write useful
  laws, not only examples. (medium)

### 2.4 Determinism, trust and gaming

- **Non-determinism.** On 829 problems, the share of tasks where no two ChatGPT outputs passed tests
  identically was 76% (CodeContests), 51% (APPS) and 48% (HumanEval); temperature 0 reduces but does
  not remove it. A build that calls a model cannot be deterministic; pinning is required, as RFC 0002
  already says. (medium)
- **Gaming.** The spec cites ImpossibleBench (93% test-hacking in one configuration) for the spec
  freeze. Follow-up work on RLVR verifier gaming and specification self-correction points the same
  way: anything the generator can see, it can overfit. Held-out checks matter. (medium)
- **Trust.** Stack Overflow 2025: 33% of developers trust AI accuracy (43% in 2024); 66% name "almost
  right, but not quite" as the top frustration; 45% say debugging AI code takes longer than expected.
  "Almost right" is precisely what a checked spec rules out, and what an ambiguous spec lets through.
  (medium, secondary)
- **Content addressing.** Unison identifies definitions by hash so renames and dependency changes do
  not break references. Yan already hashes items (3.6); a pinned body is a hash reference, not text
  that can drift. (medium)

### 2.5 Declarative LLM programming (the runtime cousin)

DSPy signatures and Marvin-style AI functions declare a typed signature and let a model act at **run
time**. That is a different product: it is non-deterministic and needs a network capability on every
call. Yan Prompt (R538) owns that niche. Yan Delegate calls the model only at **authoring** time, and
the result is ordinary checked Yan. The study keeps that line sharp. (high, from the spec rows)

### 2.6 Five findings that shape the design

1. **The spec, not the model, is the product.** Every failure in 2.1 is a spec that is too long, too
   vague, or unchecked. Yan's edge is a spec that is short and checked.
2. **Weak specs are the main risk.** True-but-weak posts pass trivial bodies (3.3). The tool must
   measure spec strength, not only spec truth.
3. **Disagreement is the best question.** Two passing bodies that differ on one input is the most
   useful thing to show a human (TiCoder, Clover).
4. **Pin, never regenerate silently.** Non-determinism (2.4) means a body is chosen once and kept
   while it stays valid.
5. **Hide something from the generator.** Overfitting to visible examples is measured and common.

## 3. The current sketch, tested

### 3.1 What RFC 0002 D10 gets right

The source is the contract and the body is a pinned, checked artefact; `yan build` never calls a
model; with no body the item is a Yan Agent hole. That design survives every finding above and the mix
keeps it.

### 3.2 What it leaves open

The RFC's four questions: regeneration stability when the header changes, whether body review is
required, how strong contracts must be, and how `out` reads in quantified posts. Section 6 answers the
first three; the fourth is settled by R767 (`out` names the result in every `post`).

### 3.3 Experiments

**Strawman bodies.** The RFC example:

```
dream dedupe_emails(xs: List[str]) -> List[str] =
  post len(out) <= len(xs)
  post all i in 0..len(out): all j in 0..len(out): i == j or lower(out[i]) != lower(out[j])
  ex dedupe_emails(["A@x.io", "a@x.io", "b@x.io"]) == ["A@x.io", "b@x.io"]
  ex dedupe_emails([]) == []
  body 3f9a...c21
```

The body `[]` satisfies both `post` lines for every input. Only the two `ex` lines reject it, and a
body that special-cases them passes everything (W806 catches the literal case, not a table built
differently). The posts never say that `out` comes from `xs`, that every address in `xs` is
represented, or that the first spelling wins. The strengthened spec needs two more facts:

```
  post all i in 0..len(xs): any j in 0..len(out): lower(xs[i]) == lower(out[j])
  post out.is_subsequence_of(xs)
```

Cheap rule derived: before generation, run the posts against a few strawman bodies (empty, identity,
a constant from the first `ex`). If any passes all posts, warn that the posts do not constrain the
result and only the examples do.

**Ambiguity witnesses.** Two reasonable `slugify` bodies that both pass the MOCK spec in
`docs/surfaces.md`: body A drops every non-ASCII character; body B transliterates first
(`std.text.to_ascii`, which the hint suggests). They disagree on `"Crème brûlée"` (A gives `"crme-brle"`,
B gives `"creme-brulee"`), on `"a_b"` (separator or dropped?), on `""` and `"!!!"` (empty slug: is
`""` allowed?) and on `"a--b"` (collapse runs?). Four real product questions, none answered by the
spec, all found mechanically by running two candidates side by side. The human answer to each is one
`ex` line. This is the central mechanism of the mix (D-ASK in section 6).

**Reference specs.** `popcount` is not naturally specified by properties at all; the honest spec is
"same as this obvious loop, but faster". A reference implementation plus a `cost` bound is the
shortest strong spec for an optimization task, and the existing contract language can already express
it as `post out == naive_popcount(x)`. It needs only a name and one check: the fast body must not
call the reference.

## 4. Five proposals

Each proposal writes the same five tasks. Shared declarations used by tasks 4 and 5, written in plain
Yan and not part of any proposal:

```
type FetchError = Timeout() | Status(code: int) | BadJson(msg: str)

type Version = { major: int, minor: int, patch: int, pre: List[str] }
```

### 4.1 Proposal A, "Glyph": brevity first

Axis: fewest characters for a human writing specs by hand. Symbols replace keywords: `~=` marks a
delegated item, `=>` is an example, `!` a property, `?` a held-out example, `@` the pin.

```
slugify(title: str) -> str uses none ~=
  "Hello, World!" => "hello-world"
  "  a  b "       => "a-b"
  ! out.all(c -> c.is_ascii_lowercase() or c.is_ascii_digit() or c == '-')
  ! not out.starts_with("-") and not out.ends_with("-")
  ? "Crème brûlée" => "creme-brulee"
  @ 7c01e9b4a2d0

dedupe_emails(xs: List[str]) -> List[str] uses none ~=
  ["A@x.io", "a@x.io", "b@x.io"] => ["A@x.io", "b@x.io"]
  [] => []
  ! out.is_subsequence_of(xs)
  ! out.map(lower).is_unique()
  ! xs.all(x -> out.any(o -> lower(o) == lower(x)))
  @ 3f9a0c21b7e6

popcount(x: int) -> int uses none ~=
  ! out == naive_popcount(x)
  $ steps <= 12
  @ 91d2aa07f3c4

fetch_json(url: str) -> Json fail FetchError uses net, clock ~=
  ! tries <= 3
  ~ "exponential backoff from 100 ms, retry only Timeout and 5xx"
  @ e0b7714c98a1

impl Ord for Version ~=
  ! a.cmp(b) == b.cmp(a).reverse()
  ! a.cmp(b) == Less and b.cmp(c) == Less implies a.cmp(c) == Less
  Version(1, 0, 0, ["alpha"]) < Version(1, 0, 0, [])
  @ 5a5e0f11d2b9
```

- **Wins.** Very short; a spec reads like a table. `=>` example rows are the best idea here: they drop
  the repeated function name, which is pure noise in a single-function spec.
- **Loses.** `!` reads as negation to every C, Rust and JavaScript programmer. Five sigils is a lot to
  learn and none is searchable. `tries` in `fetch_json` is an invented ghost name that the core has no
  meaning for: brevity pushed the spec outside the contract language. Free variables `a`, `b`, `c` in
  the trait laws are implicitly universal, which is concise and dangerous (a typo becomes a new
  quantified variable).
- **Keep.** `ARGS => RESULT` example rows.

### 4.2 Proposal B, "Ledger": safety and explicitness first

Axis: every fact an auditor needs is in the source: who generates, with what budget, who reviewed,
what the solver proved, what is withheld.

```
delegate slugify(title: str) -> str uses none =
  spec
    post out.all(c -> c.is_ascii_lowercase() or c.is_ascii_digit() or c == '-')
    post not out.starts_with("-") and not out.ends_with("-")
    ex slugify("Hello, World!") == "hello-world"
    ex slugify("  a  b ") == "a-b"
  withhold
    ex slugify("Crème brûlée") == "creme-brulee"
  generator agent(model: "sonnet", repairs: 3, budget_tokens: 20000)
  review required
  body 7c01e9b4a2d0 status proven reviewed_by "atbraz" on 2026-11-04

delegate fetch_json(url: str) -> Json fail FetchError uses net, clock =
  spec
    ex with fake_net([Timeout(), Ok("{}")]) fetch_json("u") == Json.object([])
    ex with fake_net([Status(404)]) fetch_json("u") fails Status(404)
  ceiling uses net, clock
  forbid std.fs, std.proc
  generator agent(model: "sonnet", repairs: 3)
  review required
  body e0b7714c98a1 status tested reviewed_by none
```

(The other three tasks follow the same pattern and are omitted; they add nothing new.)

- **Wins.** Nothing is implicit. `withhold` is right: examples the generator never sees are the
  strongest guard against overfitting (2.4). `review required` as a per-item policy is useful for
  money and auth code.
- **Loses.** Volatile facts (model name, budget, reviewer, date) are now in hashed source, so swapping
  models or re-reviewing churns every item hash and every downstream dependency. That breaks the point
  of content addressing. `ceiling` repeats `uses`, which is already a ceiling in Yan. The model name
  in source ties a language artefact to a vendor. Twice the length of the others.
- **Keep.** Withheld examples. A per-item review policy. Move everything else to
  `.yan/provenance.jsonl` (21.5), which already has `author`, `prompt_hash`, `status`.

### 4.3 Proposal C, "Oracle": expressive power first

Axis: say as much as possible about what you want, in as many spec styles as fit: reference
implementations, laws over all inputs, partial skeletons, trait laws, cost.

```
want popcount(x: int) -> int uses none =
  pre x >= 0
  like naive_popcount
  cost steps <= 12

want slugify(title: str) -> str uses none =
  ex "Hello, World!" => "hello-world"
  law s: str -> slugify(slugify(s)) == slugify(s)
  law s: str -> slugify(s).all(c -> c.is_ascii_lowercase() or c.is_ascii_digit() or c == '-')
  law s: str -> slugify(s.upper()) == slugify(s)

want dedupe_emails(xs: List[str]) -> List[str] uses none =
  ex ["A@x.io", "a@x.io", "b@x.io"] => ["A@x.io", "b@x.io"]
  law xs: List[str] -> dedupe_emails(dedupe_emails(xs)) == dedupe_emails(xs)
  law xs: List[str], ys: List[str] -> dedupe_emails(xs + ys).starts_with(dedupe_emails(xs))
  post out.is_subsequence_of(xs)

want fetch_json(url: str) -> Json fail FetchError uses net, clock =
  sketch
    var wait = 100.ms
    for attempt in 0..3
      match http.get(url)
        Ok(r) if r.status < 300 -> return json.parse(r.body) else BadJson(...)
        Ok(r) if r.status < 500 -> fail Status(r.status)
        _ -> clock.sleep(wait)
      wait = ...
    fail Timeout()

want impl Ord for Version
  laws Ord
  ex Version(1, 0, 0, ["alpha"]) < Version(1, 0, 0, [])
  ex Version(1, 0, 0, ["alpha", "1"]) < Version(1, 0, 0, ["alpha", "beta"])
```

- **Wins.** `like REF` turns "make this faster" into a two-line spec, and it is the strongest spec
  there is (equivalence). `law` lines (metamorphic relations: idempotence, prefix stability, case
  insensitivity) catch more bugs per line than examples and are what agents write well (2.3).
  `sketch` with `...` holes is Sketch and Hazel brought to the agent loop: the human writes the
  control structure that matters (which statuses retry) and delegates the rest. `laws Ord` pulls a
  trait's documented laws in as the spec.
- **Loses.** Many ways to say one thing. `law` needs input generators that std does not have (gap).
  `sketch` blurs who owns the body: a hand-written skeleton inside a generated artefact.
- **Keep.** `like`, `law`, `sketch`, `want impl ... laws`.

### 4.4 Proposal D, "Hole": agent token cost and tooling first

Axis: zero new grammar. A `.ydl` file is plain Yan headers with contracts, a `...` body and a pin
line. The constrained-decoding grammar is plain Yan's; the agent's phase-1 output (21.1) is already a
valid `.ydl` file.

```
slugify(title: str) -> str uses none =
  post out.all(c -> c.is_ascii_lowercase() or c.is_ascii_digit() or c == '-')
  post not out.starts_with("-") and not out.ends_with("-")
  ex slugify("Hello, World!") == "hello-world"
  ex slugify("  a  b ") == "a-b"
  ...
  body 7c01e9b4a2d0

popcount(x: int) -> int uses none =
  pre x >= 0
  post out == naive_popcount(x)
  cost steps <= 12
  ...
  body 91d2aa07f3c4
```

(`dedupe_emails`, `fetch_json` and the `impl` are the same pattern.)

- **Wins.** The insight of the whole study: **Yan Delegate is the spec gate's phase 1, persisted.**
  The spec gate already makes agents write a frozen header with `...`; the delegate file is where that
  frozen spec lives after the body exists, so a human reviews it once and it governs every later
  regeneration. No new parser work; `yan view --as yn` is the identity on the header.
- **Loses.** Nothing distinguishes an intentional delegate from a forgotten hole. No place for hints,
  withheld examples, laws or references. Repeating `slugify(` in every `ex` is noise.
- **Keep.** The framing, and the rule that every delegate header is a valid plain Yan header.

### 4.5 Proposal E, "Want": readability and learnability first

Axis: a reviewer who has never seen Yan reads the spec aloud and knows what was asked. Words over
symbols, positive and negative forms, permissions spelled out.

```
want slugify(title: str) -> str uses none
  given "Hello, World!" expect "hello-world"
  given "  a  b " expect "a-b"
  always out.all(c -> c.is_ascii_lowercase() or c.is_ascii_digit() or c == '-')
  never out.starts_with("-") or out.ends_with("-")
  may call std.text.to_ascii
  prefer "single pass, no regex"

want fetch_json(url: str) -> Json fail FetchError uses net, clock
  given fake_net([Timeout(), Ok("{}")]), "u" expect Json.object([])
  given fake_net([Status(404)]), "u" expect fail Status(404)
  never retries a 4xx
  prefer "exponential backoff from 100 ms, at most 3 tries"
```

- **Wins.** `want` is the right keyword: it says what the item is (a wish with a contract), it reads
  as English, and it is four letters. `never P` is clearer than `post not (P)` for safety facts, and
  security reviewers think in nevers. `prefer` as explicitly non-binding prose is honest.
- **Loses.** `given ... expect` is long, and `never retries a 4xx` slid into prose the checker cannot
  read (the COBOL and AppleScript trap: English-shaped syntax invites English that does not parse).
  `always` is just `post`. `may call` is a whitelist of callees, which is fragile and duplicates
  capabilities.
- **Keep.** `want`, `never`, `prefer`.

The samples do not say the same amount. A, B, D and E carry the MOCK spec's facts (two examples, two

repeated `slugify(` in each `ex`.

## 6. The mix: recommended design

### 6.1 One sentence

A `.ydl` file holds `want` items: a plain Yan header plus a checkable spec; `yan want` generates a
body with the agent loop, asks the human about every input where candidate bodies disagree, and pins
the chosen body by hash in a generated Yan Agent file that `yan build` checks and never regenerates.

### 6.2 Syntax

```
--- Turns a title into a URL slug.
want slugify(title: str) -> str uses none =
  ex "Hello, World!" => "hello-world"
  ex "Crème brûlée" => "creme-brulee"
  post out.all(c -> c.is_ascii_lowercase() or c.is_ascii_digit() or c == '-')
  never out.starts_with("-") or out.ends_with("-") or out.contains("--")
  law s: str -> slugify(slugify(s)) == slugify(s)
  held "a_b" => "a-b"
  prefer "single pass, no regex"
  body 7c01e9b4a2d0

want dedupe_emails(xs: List[str]) -> List[str] uses none =
  ex ["A@x.io", "a@x.io", "b@x.io"] => ["A@x.io", "b@x.io"]
  ex [] => []
  post out.is_subsequence_of(xs)
  post out.map(lower).is_unique()
  post xs.all(x -> out.any(o -> lower(o) == lower(x)))
  body 3f9a0c21b7e6

want popcount(x: int) -> int uses none =
  pre x >= 0
  like naive_popcount
  cost steps <= 12
  body 91d2aa07f3c4

want fetch_json(url: str) -> Json fail FetchError uses net, clock =
  ex with fake_net([Timeout(), Ok("{}")]): "u" => Json.object([])
  ex with fake_net([Status(404)]): "u" => fail Status(404)
  never net.calls() > 3
  sketch
    for attempt in 0..3
      match http.get(url)
        Ok(r) if r.status < 300 -> return json.parse(r.body) else BadJson(...)
        Ok(r) if r.status < 500 -> fail Status(r.status)
        _ -> ...
    fail Timeout()
  body e0b7714c98a1

want impl Ord for Version =
  laws Ord
  ex Version(1, 0, 0, ["alpha"]) < Version(1, 0, 0, [])
  ex Version(1, 0, 0, ["alpha", "1"]) < Version(1, 0, 0, ["alpha", "beta"])
  prefer "semver 2.0 section 11 precedence"
  body 5a5e0f11d2b9
```

**MOCK grammar** (non-normative, in the style of `docs/surfaces.md`):

```
want      = "want" (header | "impl" path "for" type) "="
            NEWLINE INDENT {clause} [sketch] ["body" HASH NEWLINE] DEDENT
header    = NAME [tparams] "(" [params] ")" ["->" type] ["fail" type] ["uses" caps]
clause    = "pre" expr | "post" expr | "cost" bounds        -- as Yan, unchanged
          | "ex" [with] args "=>" result                    -- example row
          | "ex" expr                                       -- full Yan form, still allowed
          | "held" [with] args "=>" result                  -- withheld from the generator
          | "never" expr                                    -- post not (expr)
          | "law" binders "->" expr                         -- for all generated inputs
          | "like" path                                     -- same results as a reference
          | "laws" path                                     -- the trait's laws as spec
          | "reuse" path {"," path}                         -- callees the body may prefer
          | "prefer" STRING                                 -- prose, generator only
with      = "with" expr ":"                                 -- handler for this row
args      = expr {"," expr}                                 -- one per parameter
result    = expr | "fail" expr
binders   = NAME ":" type {"," NAME ":" type}
sketch    = "sketch" NEWLINE INDENT yan-body DEDENT         -- a Yan body with ... holes
```

Every word is soft (13.1, R347), so `want`, `held`, `never`, `law`, `like`, `laws`, `reuse`,
`prefer`, `sketch` and `body` stay usable as names. Clause order is free in source; the canonical
printing (N3) is the order above: `pre`, `ex`, `post`, `never`, `law`, `like`, `laws`, `cost`, `held`,
`reuse`, `prefer`, `sketch`, `body`.

### 6.3 What each piece lowers to (N1: all lowering, no engine)

| Delegate form | Plain Yan after lowering | Notes |
| --- | --- | --- |
| `want f(...) -> T uses C =` | `f(...) -> T uses C =` with the pinned body, or `...` (R212) if none | header is a valid Yan header, unchanged |
| `ex a, b => r` | `ex f(a, b) == r` | `=> fail e` lowers to the existing failure example form |
| `ex with h: a => r` | `ex with h: f(a) == r` | handler-bound example; needs `with` in `ex` (gap, 7) |
| `held a => r` | `ex f(a) == r` in the item's hash; hidden from `hole_context` and the generator prompt | see 6.4 |
| `never P` | `post not (P)` | |
| `law x: T -> P` | a `test_` function over a seeded std input generator | needs a std property-testing module (gap, 7) |
| `like g` | `post out == g(args...)`, plus a check that the body never calls `g` | `g` must be pure (8.4) |
| `laws Ord` | the trait's law items, instantiated at the impl | needs trait laws as items (gap, 7) |
| `reuse`, `prefer` | stage-0 metadata, outside the item hash, like docstrings | generator input only |
| `sketch` | the body, with its holes filled | the filled body is what is pinned |
| `body HASH` | resolves to the item in the generated body file | |

Because every form lowers to checked Yan Core, Yan Delegate takes route 1 of R568 and keeps N4, N7
and the one back end. No surface engine.

### 6.4 Semantics: the framework

**D-PIN. Pinned bodies, valid against a spec, not for one.** `yan want` writes bodies to a generated
Yan Agent file beside the source (`slugs.ydl` gives `slugs.ydl.yag`), headed with a generated-file
line, and writes the body's item hash on the `body` line. `yan build` checks that the hash resolves,
that the body has the header's exact signature, and that it meets every clause (proved, refuted, or
runtime-checked under R211). It never calls a model. A hand edit to the body file changes its hash
and fails the build with a pointer to `yan adopt` (below).

**D-STICK. Sticky bodies.** When the spec changes, `yan want` first checks the old body against the
new spec. If it still passes, it stays; only the `body` line is rewritten if its hash moved. A body
is regenerated only when it fails, or on `yan want --fresh NAME`. This answers the RFC's stability
question and the non-determinism finding: no silent churn.

**D-ASK. Ambiguity witnesses: the spec is done when the bodies agree.** Before pinning, `yan want`
generates k candidates (default 3) that all pass the spec, runs them differentially on generated and
boundary inputs, and for every input where two disagree writes a question into the source:

```
  ex "a--b" => ?        -- candidates gave "a-b" and "a--b"
  ex "" => ?            -- candidates gave "" and fail
```

The human replaces `?` with the intended answer (or deletes the line to accept any), and generation
resumes. `?` lines are not valid in a build. This turns spec strength from a review judgement into a
mechanical loop, it is TiCoder's measured gain built into the toolchain, and it makes the cost of a
vague spec visible at authoring time instead of in production.

**D-STRAW. Strawman check.** Before D-ASK, posts are run against trivial bodies (empty, identity,
the first example's result as a constant). A post set that admits any of them is reported: "posts do
not constrain the result; only the examples do". Cheap, and it catches the RFC's own example.

**D-HOLD. Held-out rows.** `held` rows count in the item hash and run in `yan check`, but the tool
strips them from every prompt and from `hole_context`. They are the per-item version of 21.6's
held-out tests. For strong separation a package may keep held rows in a sibling `NAME.held.ydl` that
`yan mcp` never serves (open question 4).

**D-CEIL. The header is the ceiling.** `uses` and `fail` in the header bound the body, as in all of
Yan; the body may use less. The five facts (law 4) stay visible because the body is ordinary Yan
Agent. No separate allow or forbid lists (rejected from B and E).

**D-ADOPT. The escape hatch.** `yan adopt NAME` moves a delegate out: the pinned body becomes
hand-written plain Yan in the target `.yn` file with the spec lines as its contracts, and the `want`
item is removed. Delegation is a choice per item, reversible in one command. This is what keeps the
surface opinionated without being obnoxious: it never traps a body.

**D-REVIEW. Review policy by level, record in provenance.** Bodies are written by a model, so 21.5
already records them as model-authored. At `--level release`, every pinned body needs status
`proven`, or status `tested` plus a human review record in `.yan/provenance.jsonl`. A `want` item in a
module that handles money, auth or `ffi` defaults to requiring review. Model name, budget and
reviewer never appear in source (rejected from B: they would churn item hashes).

**D-FREEZE. Generation never edits the spec.** The existing spec freeze (P006, R675, W806) applies
unchanged: the generator may not touch any clause, and a `STOP: reason` from the agent is surfaced as
a question on the item.

### 6.5 Why this mix

| Taken from | What | Why |
| --- | --- | --- |
| A Glyph | `ARGS => RESULT` example rows | removes the repeated name; table-shaped, scannable |
| B Ledger | `held`; review policy | overfitting guard; audit where it matters |
| C Oracle | `like`, `law`, `laws`, `sketch` | strongest specs per line; skeleton for the parts a human must own |
| D Hole | header is plain Yan; the framing "spec gate, persisted" | no new header grammar; reuses the agent loop as is |
| E Want | `want`, `never`, `prefer` | reads aloud; nevers for safety; honest non-binding hints |
| Research | D-ASK, D-STRAW, D-STICK | TiCoder, nl2postcond, non-determinism results |

Rejected on purpose: sigils for clauses (A), vendor and reviewer facts in source (B), English clauses
the checker cannot read (E), callee whitelists (B, E), and any run-time model call (that is Yan
Prompt's niche, R538).

### 6.6 Keyword: `want` over `dream`

`dream` (RFC 0002) is evocative but suggests something loose and unbounded, the opposite of a pinned,
checked body. `want` states the relationship exactly: the human wants this contract met, and the body
is whatever meets it. It is shorter, reads in a sentence ("want slugify of title, returning str"),
and pairs with the command `yan want`. Alternatives considered: `delegate` (long, echoes the surface
name but adds nothing in text), `wish` (too soft), `spec` (collides with Yan Spec 言规, `.ysp`), `ask`
(reads as a run-time call). Decision is the lead's (open question 1).

## 7. Open questions and gaps

1. **Keyword.** `want` (recommended) or keep `dream`.
2. **`law` needs generators.** Spec has bounded quantifiers in contracts but no std module for random
   or enumerated inputs. Options: a small `std.prop` (seeded, deterministic, shrinking), or limit
   `law` to bounded domains the solver can enumerate. Either is a core or std RFC, not this surface.
3. **`ex with h:` rows.** Handler-bound examples need the `with` binding to be legal inside `ex`.
   Check spec 7 and 8.4; if not legal, this is a small core gap that also helps Yan Agent tests.
4. **How hidden is `held`?** Same file (simple, but an agent with file access can read it) or a
   sibling file the agent server never serves (strong, one more file).
5. **D-ASK budget.** Default candidates k = 3 and the input generator budget; whether CI reruns D-ASK
   (it should not: it calls a model) or only checks that no `?` rows remain.
6. **`laws` as items.** Trait laws (Ord antisymmetry, transitivity) need to be stated as checkable
   items on the trait. That belongs in spec 10 and is useful far beyond this surface.
7. **Body file per item or per source file.** One `.ydl.yag` per `.ydl` (recommended, Tessl's 1:1) or
   a shared generated module per package.
8. **Proof bodies.** Should `yan want` also generate `lemma` and loop `invariant` lines to raise a
   body from `tested` to `proven` (AutoVerus-style)? Recommended yes, as part of the same pinned item.
9. **Eval hook.** D-ASK and D-STRAW are measurable: the R567 harness could report how many questions
   a spec raises and how often strawmen pass, on the same tasks as the main runs.
